| 2026-10-19 | Omitted secrets (0.12 verification V-01): in `ConnectionSettings.Normalize` (Connect and import lists) a password field that is left out of the request and kept from the store counts as reused, exactly like `********`, so a changed destination needs the secret typed again. Usenet servers, indexers and download clients already turn an omitted secret into empty/default. **Behaviour change:** API clients that update a connection's URL/host without sending the secret get "Enter the … again" | The reviewer sent a stored webhook password to their own URL by omitting the field |

| 2026-10-19 | Data folder guard (V-02): `DataFolderGuard`/`AppPaths.FolderProblem` refuses any folder StreamZH writes to (completed, incomplete, NZB, NZB backup, watch, category, torrent save path, root folder, recycle bin, backup folder, Renamer/Organize/rename/import targets) that is inside the data folder outside `downloads/` (`Backups/` for backups) or that contains the data folder; symlinks/junctions of the existing part are resolved. Tests that kept their folders in the test data folder now use `<data>/downloads/…` | An Admin pointed a category at `<data>/tools` and planted `par2`; the same root cause could plant a key into `<data>/keys` |
| 2026-10-19 | Tool manifest (V-02): at installation the SHA-256 of every file of `<data>/tools/<tool>` is stored in Config `ToolManifest` (the database, as private as the data folder; not in the tool folder, which a planted file could fake). `PostProcessTools.Find` uses the installed copy only while the folder holds exactly those files with those hashes (no extra file, no link), checked at every Find (= before every run, version probe and tools page); hashes are cached per file by size, write and creation time. An unverified copy is skipped with a problem text and `ToolInstaller.Installed` reports it as not installed. **Behaviour change:** tools installed by 0.11 have no record; with automatic installation on (default) they are installed again at the next start, otherwise Settings → Tools shows "Install" | Trust on first use would have trusted exactly the planted files |
| 2026-10-19 | Setup without code (V-03): only when the connection is from this computer **and** the Host is an IP literal, `localhost`/`*.localhost` or one of this computer's names (`HostAccess.IsThisComputersName`); otherwise the setup code is needed | DNS rebinding from a page in the browser on the server, and header-less tunnels on the same host, looked like "this computer" |
| 2026-10-19 | Owner-only host settings (V-04, V-11): application URL, bind address, port, URL base, HTTPS on/off, HTTPS port, certificate path and password (`HostOwnerOnlyChanges`); Admins can still rename the instance, the web app shows the rest read-only. Cross-site check: when `Sec-Fetch-Site` is present only `same-origin`/`none` pass (custom headers and the API key still first); the Origin fallback is only for browsers without it | The application URL is trusted as StreamZH's own origin and host, so an Admin could make an attacker domain trusted; an Admin could expose an instance bound to 127.0.0.1 |
| 2026-10-19 | Local host names (V-05): picked the safer option: only IP literals, `localhost`/`*.localhost`, this computer's names (host name, FQDN, `<host>.local`), the application URL and "Allowed host names" get the sign-in-free access. `nas`, `*.local`, `*.lan`, `*.home.arpa` are no longer trusted by default. **Behaviour change:** users of "Disabled for local addresses"/External who open StreamZH by such a name get the sign-in page (the log names the host to add) until they add it under Allowed host names | Any LAN device can answer mDNS/LLMNR/DHCP-DNS for these names and rebind them; resolving them ourselves would not help against a rebinding answer |
| 2026-10-19 | Host header (V-06): StreamZH reads the Host from the raw header (`HostAccess.ParseHostHeader`, never throws) everywhere it judges it, and a first middleware answers 400 "Invalid Host header." when `Request.Host` would throw (bad punycode such as `xn--nas`), before anything else touches it | One stack trace and a 500 per request otherwise |
| 2026-10-19 | Login throttle (V-07): account locks are per client network (IPv4 /24, IPv6 /64, 10 failures/15 min); a second, global account limit (100/15 min) does not apply to networks the account signed in from since the start; per-address limit 30 as before. A browser with a valid session of the same account is neither blocked nor counted. Memory: entries expire after 15 min; above 20,000 entries the least recently used 10 % go (exact order by a counter), never a global reset. Trade-off: an attacker with many networks gets 10 guesses per network until the global limit stops them, and the global limit can still lock out a new network of the owner (not a known one) | The old global per-account lock let anyone lock the owner out for 15 minutes, and `Clear()` at 10,000 keys reset everything |
| 2026-10-19 | Client IP header (V-08): new owner-only setting `ClientIpHeader` (auto, x-forwarded-for, x-real-ip, cf-connecting-ip). Auto: X-Forwarded-For (right to left past trusted hops) or X-Real-IP, whichever is present; if both are present and disagree the request counts as coming from the proxy itself and a warning is logged once. Trade-off: in that conflict case all clients behind such a proxy share one counter until the owner picks the header | With a proxy that only sets X-Real-IP and passes the client's X-Forwarded-For on, the client chose its own address; with an XFF-only proxy (Caddy, HAProxy, Apache) the client chooses X-Real-IP; without knowing the proxy neither header can be believed when they differ |
| 2026-10-19 | Cookies from before 0.12 (V-09): on first use the cookie gets a session and is replaced (as before), and a marker row `legacy-<sha256(user, issued, expires, version)>` is stored in Sessions; the same old cookie gets the same session for 60 s more (parallel requests of a page load), then it is refused, also after a restart. Markers are cleaned like sessions after 31 days (old cookies live at most 30) and do not count as sign-ins | Copies of a pre-0.12 cookie kept working until expiry; no forced re-login after the update |
| 2026-10-19 | Outbound guard (V-10): requests restricted to another host than the indexer's must also avoid private ranges (10/8, 172.16/12, 192.168/16, 100.64/10, fc00::/7, fec0::/10), unless the host is another configured indexer or download client (`IConfiguredServiceHosts`, cached 30 s); the indexer's own host stays unrestricted. With an outgoing proxy carrying the request (settings proxy or `HTTP(S)_PROXY`) a name that does not resolve locally is refused. Remaining gap (documented): the proxy resolves again, so a DNS answer that changes between our check and the proxy's lookup can reach a private address. **Behaviour change:** an indexer whose links name another LAN host (e.g. Jackett's base URL set to an IP while StreamZH uses its container name) must have that host configured | Blind GETs to router/NAS admin pages via feed links |
| 2026-10-19 | Cross-site protection (0.12, S1-01/S1-07): every POST/PUT/PATCH/DELETE must show it comes from StreamZH's own pages: `Sec-Fetch-Site` same-origin/none, an `Origin` equal to the request host (default ports: a Host without port matches only an Origin on 80/443) or the application URL, or a header other sites cannot add without CORS (`X-StreamZH-Request`, sent by the web app's fetch client and the SignalR client; `X-Api-Key`; the tray header). Requests signed in with the API key are exempt. Applies to every identity, also anonymous (setup, login, invitations). `/hub` also refuses GETs with a foreign Origin. **Behaviour change:** scripts that use a cookie or Basic credentials for changing calls must send `X-StreamZH-Request: 1` (or use the API key) | A token-free scheme that covers bodyless, raw-body and multipart endpoints alike and needs nothing from API clients; SameSite=Strict does not stop same-site pages (other ports, sibling subdomains) |
| 2026-10-19 | DNS rebinding (0.12, S1-01): instead of rejecting unknown Host headers with 400, the sign-in-free identities (local addresses, External) are only given when the Host is a name an attacker cannot point at StreamZH: any IP literal, `LocalAddress.IsLocalHost` names (localhost, single-label, .local/.lan/.home.arpa/.localhost), this computer's names, the application URL's host and "Allowed host names" (`*.example.com` allowed). Other hosts fall back to the normal sign-in | A rebinding page's origin is always a DNS name it controls; IP literals and local names are safe, so LAN users by IP or `nas.local` notice nothing, and a wrong name degrades to the sign-in page instead of an error page |
| 2026-10-19 | External authentication (0.12): only from "Trusted proxies"; while that list is empty, from local addresses (`LocalAddress.IsLocal`, so proxies on this host, in Docker networks and on the LAN keep working after the update). Optional "User header" (e.g. Remote-User) must be present and becomes the shown user name. Requests that do not qualify get the Forms sign-in. **Behaviour change:** a reverse proxy on a public address must be listed under Trusted proxies | Before, External let every request in, including direct ones from the internet |
| 2026-10-19 | Forwarded headers (0.12): own `ProxyForwarding` middleware (live settings) instead of ASP.NET's ForwardedHeadersMiddleware (options fixed at startup): only for a connection from a trusted proxy, X-Forwarded-For (rightmost untrusted entry, else X-Real-IP) replaces the remote address and X-Forwarded-Proto the scheme; the cookie keeps SecurePolicy SameAsRequest, which then is Secure behind an HTTPS proxy | Trusted proxies can change without a restart; same semantics as KnownNetworks |
| 2026-10-19 | `?apikey=` only on `/hub` (0.12, S1-04); the iCal feed takes `?token=` with its own read-only `CalendarFeedToken` (config key, created on first use, "Create new link" in the iCal dialog, admin only). **Behaviour change:** API clients must send `X-Api-Key`; iCal links from before 0.12 stop working and must be copied again | A key in an address ends up in histories, logs and shared calendar links; the feed needs no more than read access |
| 2026-10-19 | Sessions (0.12, S1-10, M027): a `Sessions` table (id = 256-bit random, user, created, last seen, persistent); the cookie carries the id as claim `streamzh:sid` and is valid only while the row exists (cached 30 s, dropped at once on logout). Logout deletes the row. Cookies from 0.11 (no id) get a session on their next request instead of being refused. Without "Remember me" (now unticked by default) the cookie is a browser-session cookie with a 24 h sliding ticket; with it 30 days sliding. Cookie path = URL base.
